# Bella OS — Decisões (ADRs)

> Uma entrada por decisão. Formato: contexto → decisão → consequências → como reverter. Status: `aceita`, `proposta`, `substituída por ADR-x`. Novas decisões vão ao final; nunca reescreva o histórico.

## ADR-001 — Monólito modular TypeScript em monorepo pnpm (aceita, 2026-09-09)
**Contexto:** três superfícies (cliente, KDS, admin), regras financeiras críticas, equipe de um dev + agentes, custo baixo.
**Decisão:** monorepo pnpm com `apps/api` (Fastify), `apps/web` (Next.js), `packages/{db,domain,contracts,config}`. Domínios separados por pasta e por contrato dentro da API.
**Consequências:** um deploy por app; domínio testável sem browser; sem rede entre módulos. Exige disciplina: módulo não acessa tabela de outro.
**Reverter:** extrair um módulo para serviço próprio quando houver motivo medido (carga ou equipe), mantendo o contrato.

## ADR-002 — PostgreSQL como único banco; dinheiro em `bigint` centavos (aceita)
**Contexto:** transações, constraints, RLS, concorrência de fechamento e pagamentos.
**Decisão:** Postgres 16. Nenhum `float` para dinheiro. Helper único de arredondamento half-even.
**Consequências:** todo cálculo passa por `packages/domain/money.ts`; testes de centavos obrigatórios.

## ADR-003 — Drizzle ORM com migrations SQL versionadas (aceita)
**Contexto:** precisamos de `SET LOCAL`, índices parciais, triggers e RLS explícitos.
**Decisão:** Drizzle + drizzle-kit; SQL manual permitido em migrations para constraints/RLS/triggers.
**Alternativa descartada:** Prisma (abstrai demais transação/RLS).

## ADR-004 — Multi-tenant por coluna `tenant_id` + RLS como segunda camada (aceita)
**Contexto:** SaaS futuro; vazamento entre restaurantes é falha inaceitável.
**Decisão:** um banco/schema; `tenant_id NOT NULL` em toda tabela de negócio; contexto de tenant obrigatório na camada de repositório; RLS com `current_setting('app.tenant_id')` ativado nas tabelas de negócio; usuário de aplicação sem `BYPASSRLS`. Tenant = uma unidade; `organizations` opcional agrupa unidades.
**Consequências:** toda transação começa com `SET LOCAL app.tenant_id`; testes de vazamento cruzado são gate de saída da Fase A.
**Reverter:** schema-per-tenant ou banco-per-tenant só se um cliente exigir isolamento físico (custo alto, não previsto).

## ADR-005 — Better Auth para staff; sessão de mesa assinada para cliente; dispositivo + PIN para operação (aceita)
**Contexto:** auth artesanal é risco; restaurante usa dispositivos compartilhados; cliente não quer criar conta.
**Decisão:** Better Auth (email+senha, sessões em Postgres) para staff/admin. Dispositivos (KDS, caixa) pareados por código e com token de longa duração escopado. Ações sensíveis exigem PIN de operador (argon2id, bloqueio por tentativas). Cliente recebe cookie httpOnly com token HMAC escopado a uma sessão de mesa.
**Consequências:** três tipos de credencial na API; middleware resolve ator uniforme `{ type, id, tenantId, permissions }`.
**Risco registrado:** dependência de biblioteca de terceiros para auth; mitigação: adapter isolado em `identity/auth-provider.ts`; se Better Auth se mostrar inadequado na Fase A, trocar por Lucia-style com Oslo antes de existir usuário real. **Sonnet deve confirmar a versão atual e a API do Better Auth na documentação oficial antes de implementar** (regra da seção 16 do handoff).

## ADR-006 — Tempo real via SSE com outbox em Postgres (aceita)
**Contexto:** KDS precisa de push; mutações são HTTP; queremos reconexão simples.
**Decisão:** eventos gravados em `domain_events` na mesma transação da mutação; endpoint SSE por canais; replay por `Last-Event-ID`; polling de segurança no KDS a cada 20 s; instância única no início, `LISTEN/NOTIFY` quando houver mais de uma.
**Descartado:** WebSocket (bidirecional desnecessário), Supabase Realtime (acoplamento), Redis (infra extra).

## ADR-007 — Idempotência por chave do cliente em toda mutação crítica (aceita)
**Decisão:** header `Idempotency-Key` obrigatório em criação de pedido, pagamento, sessão de mesa e transições; tabela `idempotency_keys` com resposta armazenada; corpo diferente com mesma chave → `409`.

## ADR-008 — Ledger append-only por comanda; totais reconstruíveis (aceita)
**Decisão:** `ledger_entries` sem UPDATE/DELETE (privilégio revogado + trigger). Saldo = soma. `tab_closures` guarda snapshot para conferência. Teste de reconciliação compara ledger × itens × pagamentos.

## ADR-009 — Pagamento manual no MVP; sem PSP, sem TEF, sem fiscal (aceita)
**Contexto:** Bella já tem maquininha/PIX; integração fiscal exige decisão jurídica (SAT/NFC-e).
**Decisão:** caixa registra forma e valor. `payments.external_ref` e estados `pending/failed` reservados para PSP futuro. Nenhuma promessa fiscal até Victor decidir (pergunta Q5 em `PRODUCT_CONTEXT.md`).

## ADR-010 — QR fixo por mesa + confirmação de sessão configurável (aceita)
**Contexto:** QR impresso não pode rotacionar; risco de pedido remoto/prank.
**Decisão:** `tables.qr_code` curto e não sequencial; sessão aberta por cliente nasce não verificada quando `customer_order_mode ≠ direct`; primeiro pedido aguarda confirmação do salão; limite de valor para sessão não verificada; rate limit. Modo `direct` disponível para quem aceitar o risco.

## ADR-011 — Cloud-first no Railway; degradação consciente sem internet (aceita)
**Contexto:** custo e simplicidade vs. dependência de internet do restaurante.
**Decisão:** API + web + Postgres no Railway (staging e production). KDS/caixa não fazem mutação offline; mostram estado e bloqueiam. Recomendação formal de failover 4G ao Bella. Impressão via agente local na Fase E.
**Reverter:** "modo servidor local" só se a operação provar necessidade.

## ADR-019 — IDs de aplicação são UUID v7 (`uuidv7` npm) (aceita, M1)
**Contexto:** DOMAIN_MODEL.md pedia UUID v7 (ordenável por tempo); Node 24 não tem gerador v7 nativo (`crypto.randomUUID()` é v4).
**Decisão:** pacote `uuidv7` (versão fixada conferida no npm em 2026-09-09) envolvido em `packages/domain/src/id.ts` (`newId()`, `isUuid()`). O banco mantém `gen_random_uuid()` (v4) como default de coluna — usado só se a aplicação não fornecer o ID explicitamente (nunca deveria acontecer em código novo).
**Consequência:** um único ponto para trocar a biblioteca se necessário; testes de propriedade garantem unicidade e ordenação crescente.

## ADR-020 — Um único papel de banco restrito (`bella_app`); dono do banco também migra e semeia (aceita, M1)
**Contexto:** o plano original do M1 previa dois papéis (`bella_migrator` dono + `bella_app` restrito). Implementação simplificou para um: o usuário já provisionado como dono do banco (`bella` local/CI, o usuário do Railway em produção) roda migrations e seed; só `bella_app` (sem LOGIN/SUPERUSER/BYPASSRLS, criado pela migration) é novo.
**Motivo:** um papel administrativo a menos por ambiente, uma senha a menos para gerenciar, sem perda de segurança — o que protege o RLS é `bella_app` não ser dono e não ter BYPASSRLS (provado no teste (d) do M1), não a existência de um segundo papel administrativo.
**Consequência:** `DATABASE_URL` = dono (migrations/seed/inspeção); `APP_DATABASE_URL` = `bella_app` (é o que a API deveria usar a partir do momento em que módulos de negócio existirem, M2+). `docs/ACTIVE_PLAN.md` e `docs/DOMAIN_MODEL.md §2` citavam `bella_migrator`; não existe — corrigido nesta atualização.

## ADR-021 — RLS e o papel `bella_app` são declarados na DSL do drizzle-orm, não em SQL manual (aceita, M1)
**Contexto:** o plano original previa uma migration `--custom` hand-written para RLS/roles, por desconfiança de que a DSL de RLS do drizzle-orm (`pgPolicy`, `pgRole`, `.enableRLS()`) pudesse gerar SQL na ordem errada (política antes do papel existir) ou brigar com o comando `drizzle-kit check` (colisão de snapshot idêntico entre uma migration "custom" vazia e a anterior).
**Decisão, com evidência:** inspecionado o código instalado do `drizzle-kit` (`api.js`) e testado localmente (sem precisar de banco — `generate` é só diff de schema): `CREATE ROLE "bella_app";` sai **antes** de qualquer `CREATE TABLE`, e `CREATE POLICY ... TO "bella_app"` sai **depois** de todas as tabelas — ordem correta automaticamente. `pgRole('bella_app', { inherit: true })` é necessário explicitamente: o construtor do drizzle-orm não tem default para `inherit`, e deixá-lo `undefined` gera `WITH NOINHERIT` sem necessidade (confirmado lendo `roles.js`).
**O que continua manual:** `GRANT`/`REVOKE`/`ALTER DEFAULT PRIVILEGES` — não modelados pela DSL — apendados ao final do arquivo de migration gerado por `drizzle-kit generate` (não é mais uma migration `--custom` separada).
**Consequência:** `pnpm db:check` fica limpo (sem colisão de snapshot); RLS vive no schema TypeScript, versionada junto com a tabela, reduzindo o risco de uma tabela nova esquecer a política. Regra para o futuro: toda tabela de negócio nova usa `tenantIsolationPolicy(t.tenantId)` no array de config + `.enableRLS()` (ver `packages/db/src/schema/_rls.ts`).

## ADR-022 — `ALTER ROLE ... PASSWORD` não aceita parâmetro `$1`; usar `pg.escapeLiteral` (aceita, M1)
**Contexto:** primeira versão de `set-app-role-password.ts` usava `client.query('alter role bella_app with login password $1', [password])`, assumindo que o protocolo estendido do `pg` parametriza qualquer posição de valor em DDL. A CI provou o contrário: `syntax error at or near "$1"` — o parser de DDL do Postgres exige um literal de string nessa posição específica da gramática de `ALTER ROLE`.
**Decisão:** construir o SQL com `pg.escapeLiteral(password)` (escapa aspas simples e barras invertidas corretamente, produzindo `E'...'` quando necessário) e interpolar o literal já escapado. Coberto por teste unitário com `pg.Client` mockado que garante a query nunca contém `$1` e que uma senha com aspas simples aparece escapada.
**Licão para o projeto:** nem toda posição sintática aceita bind parameter; quando uma migration/script toca DDL com valor dinâmico, ou se evita DDL dinâmico, ou se escapa manualmente com a função oficial da biblioteca — nunca com concatenação de string crua.

## ADR-023 — Better Auth integrado via adapter Drizzle + rota catch-all manual no Fastify (aceita, M2)
**Contexto:** ADR-005 previa Better Auth para staff, mas com risco explícito de a API/versão ter mudado (KNOWN_ISSUES R-2). Pesquisa feita ao vivo em 2026-09-09 contra a versão instalada (`better-auth@1.7.3`).
**Decisões, com evidência:**
- **Sem plugin oficial para Fastify.** Confirmado na documentação e nos fontes instalados (`better-call/node`'s `toNodeHandler` lê o `req` cru como stream). Integração é uma rota catch-all (`/api/auth/*`, métodos GET/POST) que constrói manualmente um `Request` do Fetch a partir de `request.url`/`request.headers`/corpo, chama `auth.handler(request)`, e repassa a `Response` para o Fastify.
- **Parser de conteúdo desligado só para este plugin.** O handler do Better Auth lê o corpo sozinho; o parser de JSON default do Fastify já teria consumido o stream antes. Corrigido com `addContentTypeParser('*', { parseAs: 'buffer' }, ...)` registrado **dentro** do plugin `identityRoutes` — o encapsulamento do Fastify garante que isso não vaza para outras rotas (`/health`, futuros `/v1/orders`, etc.).
- **`usePlural: true` no adapter Drizzle.** Nosso schema já segue a convenção de tabelas no plural (`users`, `tenants`, ...); rodar a própria CLI (`auth generate`) contra o schema confirmou que essa opção gera `sessions`/`accounts`/`verifications` (plural) em vez do padrão `session`/`account`/`verification`.
- **CLI correta é o pacote `auth`, não `@better-auth/cli`.** `@better-auth/cli` está **deprecado** (confirmado via `npm view`: "Package no longer supported"). O pacote `auth` (mesma versão do core) é quem expõe `auth generate`/`auth migrate`/etc. hoje.
- **IDs continuam UUID v7.** `advanced.database.generateId: () => newId()` (ADR-019) — as colunas `sessions.id`/`accounts.id`/`verifications.id`/`users.id` continuam `uuid` nativo, não `text` (default do Better Auth quando ele mesmo gera o id).
- **`users.password_hash` (M1) removido.** O Better Auth modela senha em `accounts.password` (uma linha por método de login), não em `users`. O campo do M1 nunca foi usado por nenhum código; duas migrations separadas (`0001` adição pura, `0002` remoção pura) evitaram o prompt interativo de "foi renomeado?" do `drizzle-kit generate` ao misturar adição e remoção no mesmo diff.
- **Chaves de objeto do schema (`_columns.ts`) corrigidas para camelCase** (`createdAt`/`updatedAt`, eram `created_at`/`updated_at`). O adapter do Better Auth procura campos pela chave JS, não pelo nome da coluna SQL — a inconsistência do M1 só apareceu ao integrar isto. Confirmado que a troca não gera migration (drizzle-kit rastreia colunas pelo nome SQL, não pela chave do objeto).
**Consequência:** `packages/db/src/schema/auth.ts` novo (sessions/accounts/verifications, sem RLS — tabelas globais como `users`); `apps/api/src/modules/identity/{auth,routes,require-permission}.ts`.

## ADR-024 — A API passa a conectar como `bella_app` (não mais o dono) a partir do M2 (aceita)
**Contexto:** M1 provou o isolamento por RLS, mas `apps/api/src/index.ts` continuava construindo sua conexão de runtime a partir de `DATABASE_URL` (o dono do banco, que ignora RLS por padrão) — um gap identificado só ao escrever os testes de integração do M2, quando ficou claro que testar com a conexão de dono esconderia qualquer bug real de isolamento no módulo de identidade.
**Decisão:** nova variável `APP_DATABASE_URL` (conexão como `bella_app`) é o que `index.ts` usa para servir tráfego. Cai para `DATABASE_URL` apenas como conveniência de desenvolvimento antes de `pnpm db:app-role` ter sido rodado, **com aviso alto no log** (nunca silencioso). Todos os testes de integração do M2 (`auth.test.ts`, `require-permission.test.ts`) constroem a API de teste com `TEST_APP_DATABASE_URL`, não com a conexão de dono — replicando exatamente como a API roda de verdade.
**Consequência:** `DATABASE_URL` fica reservado para `packages/db` (migrations/seed/operação); `APP_DATABASE_URL`/`TEST_APP_DATABASE_URL` são o caminho real da aplicação a partir de agora. Documentado em `.env.example` e `docs/RUNBOOK_DEV.md`.

## ADR-025 — `devices` e `pairing_codes` são tabelas globais, sem RLS por tenant (aceita, M3)
**Contexto:** todas as tabelas de negócio desde o M1 usam `tenantIsolationPolicy()` (ADR-021). Ao desenhar o pareamento de dispositivo, apareceu um caso que essa regra não cobre: a troca de código (`/v1/devices/exchange`) e a autenticação por token (`X-Device-Token`) acontecem **antes** de existir qualquer contexto de tenant conhecido — o próprio propósito dessas operações é *descobrir* o tenant a partir de um segredo opaco (6 dígitos ou o token). Com RLS ativada, `bella_app` sem `app.tenant_id` definido não veria nenhuma linha de `devices`/`pairing_codes` (comportamento correto e já provado no M1 — "sem contexto, zero linhas"), tornando essas buscas impossíveis.
**Decisão:** `devices` e `pairing_codes` ficam **sem RLS**, na mesma categoria de `users`/`sessions`/`accounts`/`verifications` (ARCHITECTURE.md §4: tabelas globais, controle de acesso na aplicação). Ambas mantêm `tenant_id NOT NULL` (sabemos a qual tenant um dispositivo pertence assim que ele é resolvido). Endpoints administrativos (`listDevices`, `revokeDevice`) filtram `tenant_id` explicitamente no código da aplicação — o banco não filtra sozinho aqui, então a disciplina de sempre passar o `tenantId` do ator autenticado (nunca de entrada do cliente) é a única linha de defesa, e por isso reforçada em comentário no código-fonte (`service.ts`).
**Consequência:** uma vez resolvido o dispositivo (por token) ou processado o código (por pareamento), toda query de negócio subsequente volta a usar `withTenant()` normalmente — o padrão do M1 continua sendo a regra geral; esta é uma exceção pontual e documentada, não uma mudança de política.
**Prova:** `devices.test.ts` cobre o caso que motivou a exceção (device do tenant Demo não consegue verificar PIN de membership do tenant Bella — bloqueado pela RLS de `memberships`, que continua ativa).

## ADR-026 — `@node-rs/argon2` para hash de PIN; precisou ser `external` no build da API (aceita, M3)
**Contexto:** PIN de operador (baixa entropia) precisa de hash lento (argon2id). Candidatos pesquisados: `argon2` (node-gyp-build, pode exigir compilador nativo), `@node-rs/argon2` (napi-rs, binário pré-compilado por plataforma como pacote npm opcional separado), `bcrypt`/`bcryptjs`.
**Decisão:** `@node-rs/argon2`, confirmado instalando de verdade nesta máquina Windows (resolveu `@node-rs/argon2-win32-x64-msvc` automaticamente, sem compilador) e rodando um hash+verify reais antes de escrever qualquer código de produção (regra 12).
**Bug real encontrado e corrigido:** `pnpm build` da API falhou — o `index.js` do `@node-rs/argon2` tem `require()` condicional para o binário `.node` de **cada** plataforma (win32/darwin/linux/android × x64/arm64/ia32); o esbuild (via tsup) tentou resolver todos estaticamente e quebrou nos que não existem nesta máquina. Mesma classe de bug do `pg` no M0. Corrigido adicionando `@node-rs/argon2` ao array `external` do `tsup.config.ts`. Isso revelou um **segundo** problema, também encontrado rodando o binário compilado de verdade (não só o build): mesmo `external`, o `dist/index.js` da API não conseguia resolver `@node-rs/argon2` em runtime (`ERR_MODULE_NOT_FOUND`) porque o pnpm isola `node_modules` por pacote — `@node-rs/argon2` era dependência de `@bella/domain`, não de `@bella/api` diretamente. Corrigido declarando `@node-rs/argon2` também como dependência direta de `apps/api/package.json` (mesmo padrão já usado para `pg` desde o M0: toda dependência nativa/externa usada pelo bundle final precisa estar declarada em todo pacote que a executa em runtime, não só onde o código-fonte a importa).
**Lição geral:** `pnpm build` sozinho não é evidência suficiente para uma dependência nova — é preciso **rodar** o bundle compilado (smoke real) sempre que uma dependência nativa ou com resolução condicional por plataforma for adicionada, em qualquer pacote do monorepo, não só em `apps/api`.

## ADR-027 — Consultas de teste via conexão de dono precisam filtrar `tenant_id` explicitamente (aceita, M3)
**Contexto:** ao escrever `devices.test.ts` (dois tenants no mesmo teste), a CI provou um bug real de setup: `withTenant(ownerDb.db, tenantId, tx => tx.select().from(schema.roles))` **não filtra nada**, porque `ownerDb` é a conexão de DONO do banco, que ignora RLS por padrão (ADR-004) — `withTenant` só define `app.tenant_id`; quem de fato restringe linhas é a *policy* de RLS, e ela não se aplica ao dono. O código então fazia `.find(r => r.name === 'owner')` sobre TODOS os papéis de TODOS os tenants, e o Postgres devolvia as linhas do Bella primeiro (tenant seedado primeiro) mesmo pedindo o contexto do Demo — o teste criava uma membership do "dono do Demo" apontando, por engano, para o papel `owner` do **Bella**. O sintoma na CI foi `TENANT_MISMATCH` num teste completamente diferente (verificação de PIN), porque `role_permissions` (que tem RLS de verdade) filtrou essas linhas erradas e o JOIN voltou vazio.
**Decisão:** toda consulta de teste que usa `ownerDb` (ou qualquer conexão que ignore RLS) para buscar dados de UM tenant específico precisa de `.where(eq(tabela.tenantId, tenantId))` explícito — nunca confiar em `withTenant()` sozinho para "filtrar" quando a conexão por trás bypassa RLS. Corrigido em `devices.test.ts`, `pin.test.ts`, `require-permission.test.ts`. Os testes do M1 (`tenant-isolation.test.ts`, `audit-outbox.test.ts`) não tinham esse problema porque suas asserções de isolamento já usavam `appDb` (a conexão restrita, onde RLS de fato filtra) — auditado e confirmado ao investigar este bug.
**Lição geral:** `withTenant()`/`withoutTenant()` só têm efeito de isolamento quando a conexão por trás é `bella_app`. Usados sobre `ownerDb`, servem apenas para definir a variável de sessão (útil para inspeção/depuração), não para restringir o quê a query enxerga — qualquer filtro de tenant precisa ser explícito no `WHERE` nesses casos.

## ADR-028 — `apps/web` (Next.js 16 App Router): typegen no typecheck, fontes em duas origens, cliente HTTP com dois formatos de erro (aceita, M4)
**Contexto:** M4 é o primeiro milestone de frontend. Pesquisa ao vivo em 2026-09-09 confirmou `next@16.3.4`, `react@19.3.0` (regra 12) antes de codar.
**Decisões, com evidência:**
- **`next typegen` precisa rodar antes de `tsc --noEmit` standalone.** O App Router do Next.js 16 gera tipos (`PageProps<'/rota'>`, `LayoutProps`) em `.next/types/`; um `tsc --noEmit` isolado (fora de `next build`/`next dev`, como roda `pnpm -r typecheck`) não os encontra sozinho. Corrigido: `apps/web/package.json` → `"typecheck": "next typegen && tsc --noEmit"`. Sem isso, `pnpm typecheck` na raiz falha só para `apps/web`, mesmo com o código correto.
- **`pnpm-workspace.yaml` duplicado quebra o monorepo.** `create-next-app` gerou seu próprio `apps/web/pnpm-workspace.yaml` (com `ignoredBuiltDependencies: [sharp, unrs-resolver]`), conflitando com o da raiz. Deletado o duplicado; `ignoredBuiltDependencies` mesclado no arquivo raiz.
- **Fontes do design system vêm de DUAS origens, não uma** (`FRONTEND_GUIDELINES.md`): Schibsted Grotesk + JetBrains Mono via Google Fonts (`next/font/google`, self-hosted pelo Next), Switzer via Fontshare (não existe no Google) — carregada por `<link>` em `layout.tsx`. Confirmado de verdade com `document.fonts.check('600 16px "Schibsted Grotesk"')` etc. num browser real, não só inspeção visual.
- **Gotcha Tailwind v4 já documentado no `CLAUDE.md` global se confirmou na prática:** `var(--font-display)` sob `@theme inline` resolve vazio em `@layer base`; `globals.css` usa stack literal (`font-family: "Schibsted Grotesk", ...`).
- **Cliente HTTP (`src/lib/api.ts`) precisa reconhecer dois formatos de erro distintos.** `apiFetch()` (rotas `/v1/*`) sempre usa nosso envelope (`{ error: { code, message, request_id } }`). Já `authFetch()` (rotas `/api/auth/*`, Better Auth) pode receber **duas** formas na mesma função: a do próprio Better Auth (`{ message }` plano, quando o handler dele responde) **ou** a nossa (`{ error: { message } }`, quando a requisição nem chega ao Better Auth — ex.: 404 do próprio Fastify porque `WEB_ORIGIN`/CORS bloqueou ou a rota não bate). `extractErrorMessage()` checa as duas formas antes de cair no texto genérico. Bug real encontrado testando de verdade num browser: sem `WEB_ORIGIN` configurado no processo da API, a mensagem específica ("Rota não encontrada: ...") não aparecia — só a genérica — porque a função só checava a forma plana.
- **Achado de processo (não é bug de código):** depois de corrigir `extractErrorMessage()` e rodar `pnpm build`, testar contra um `next start` que já estava rodando **antes** do rebuild mostrou o comportamento antigo — os nomes de chunk servidos pelo navegador não batiam com os arquivos novos em `.next/static/chunks/` no disco (confirmado comparando as duas listas). `next start` carrega o build em memória na inicialização; um rebuild em disco não é pego por um processo já rodando. Corrigido matando o processo antigo e reiniciando `next start` sobre o build novo — depois disso a mensagem específica apareceu corretamente. Lição para toda sessão futura de smoke manual: **sempre reiniciar `next start`/`node dist/index.js` depois de qualquer rebuild antes de testar**, nunca assumir que um servidor de produção já em execução "pegou" o código novo.
**Consequência:** `apps/web/src/lib/api.ts`, `apps/web/src/app/layout.tsx`, `apps/web/src/app/globals.css`, `apps/web/package.json`. Playwright **não** foi instalado neste milestone (decisão consciente, ver `ACTIVE_PLAN.md`/`QA_LEDGER.md` M4) — evidência de E2E veio de testes manuais reais via browser (Claude Browser tool), com rede/console inspecionados, não só captura de tela.

## ADR-030 — `GET /v1/me/tenants` via segunda policy de RLS permissiva (`selfLookupPolicy`), não bypass (aceita, M5)
**Contexto:** M5 precisa que o front descubra a qual tenant um usuário pertence (para preencher `X-Tenant-Id` sozinho, já que ainda não existe seletor de tenant na UI — ver ACTIVE_PLAN.md M5). `memberships` tem RLS por tenant (ADR-021): sem `app.tenant_id` definido, a policy de isolamento (`tenant_isolation`, `for: 'all'`) não deixa nenhuma linha visível — é exatamente o comportamento correto e desejado (DOMAIN_MODEL.md §3, "sem contexto, zero linhas"), mas aqui é o próprio problema: não dá para descobrir o tenant usando o tenant como chave de busca. `withoutTenant()` (usado para tabelas globais como `devices`/`pairing_codes`, ADR-025) não serve — `memberships` não é uma exceção de RLS, é uma tabela normal, e o comentário do próprio `withoutTenant()` já avisa que ele não funciona para tabelas com RLS.
**Decisão:** nova função `withUser(db, userId, fn)` (`packages/db/src/tenant-context.ts`) define `app.user_id` (sem `app.tenant_id`) via `set_config` local à transação — mesmo padrão de `withTenant`/`withoutTenant`. Nova policy `selfLookupPolicy(userIdColumn)` (`schema/_rls.ts`), aplicada só em `memberships` (`schema/identity.ts`): `for: 'select'`, permissiva, `USING (user_id = app.user_id)`. Múltiplas policies permissivas para o mesmo comando são combinadas com **OR** pelo Postgres (não substituem uma à outra) — confirmado no comportamento esperado do RLS padrão (não é uma peculiaridade deste projeto, é a semântica documentada do Postgres). Resultado: um usuário enxerga suas próprias linhas de `memberships` (com `tenant_id`, `role_id`) mesmo sem contexto de tenant definido, mas continua sem enxergar linhas de OUTRO usuário nem ganhando qualquer acesso de escrita fora do fluxo normal (`INSERT`/`UPDATE`/`DELETE` continuam só sob a policy de tenant, porque a nova policy é `for: 'select'`).
**Por que não é um enfraquecimento de isolamento:** a policy nova restringe por `user_id`, não abre a tabela. Não existe cenário em que o usuário A veja a membership do usuário B — o que ele ganha é enxergar as PRÓPRIAS memberships em tenants diferentes ao mesmo tempo, que é exatamente o dado necessário para "em quais tenants eu estou" existir sem expor nada de outro tenant/usuário.
**Consequência:** `packages/db/src/tenant-context.ts` (`withUser`), `packages/db/src/schema/_rls.ts` (`selfLookupPolicy`), `packages/db/src/schema/identity.ts` (`memberships` ganha a policy), migration `0004`. `apps/api/src/modules/identity/tenants-routes.ts` (`GET /v1/me/tenants`) é o único consumidor até agora.

## ADR-031 — `guests` sem RLS (ADR-025 estendida); cookie de sessão de mesa opaco, sem biblioteca nova; concorrência resolvida com transações separadas (aceita, M6)
**Contexto:** M6 precisa que o celular de um cliente, sem nenhuma credencial prévia, abra uma sessão de mesa a partir só do QR físico e vire um `guest` identificável por um cookie.
**Decisão 1 — `guests` sem RLS por tenant:** mesmo caso de `devices`/`pairing_codes` (ADR-025) — resolver o cliente pelo token bruto do cookie acontece ANTES de existir qualquer contexto de tenant conhecido (é exatamente o dado que falta descobrir). `tenant_id`/`table_session_id` continuam `NOT NULL`; filtros de negócio por tenant continuam explícitos na aplicação depois de resolvido, nunca confiando no banco para filtrar sozinho aqui.
**Decisão 2 — cookie de sessão de mesa é opaco (hash no banco), não assinado (JWT/HMAC), e nenhuma biblioteca nova foi adicionada:** a segurança não vem de uma assinatura verificável offline, vem do valor ser alta entropia + verificado por hash no banco — mesmo modelo de confiança do token de dispositivo (M3, ADR-025). Parsear o header `Cookie` e montar o `Set-Cookie` (`HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age`) à mão (`apps/api/src/lib/cookies.ts`) é suficiente e mais simples que integrar `@fastify/cookie` só para isso — reavaliar se aparecer uma necessidade real de assinatura (ex.: JWT com claims verificáveis sem round-trip ao banco).
**Decisão 3 — concorrência real (duas aberturas simultâneas na mesma mesa) é resolvida com transações SEPARADAS, não uma única transação com catch interno:** a primeira versão tentava capturar a violação do índice único parcial de `table_sessions` (`table_sessions_open_per_table_key`) e continuar consultando dentro da MESMA transação — bug real encontrado na revisão antes mesmo de rodar a CI (não em produção): o Postgres aborta o restante de uma transação após qualquer violação de constraint, até o `ROLLBACK` — qualquer comando seguinte falharia com "current transaction is aborted". Corrigido: a tentativa de criar (`tryCreateSession`) e o fallback de entrar numa sessão já aberta (`joinExistingSession`) são duas chamadas de `withTenant()` **separadas** (duas transações distintas); a primeira, se colidir, é desfeita inteira e limpa pelo Postgres antes da segunda começar. Resultado: duas requisições simultâneas na mesma mesa nunca criam duas sessões (provado com `Promise.all` disparando as duas de verdade, não sequencialmente), e cada uma vira um `guest` novo dentro da MESMA sessão — não um erro para o segundo cliente.
**Consequência:** `packages/db/src/schema/tables.ts` (`guests` sem `.enableRLS()`), `apps/api/src/lib/cookies.ts` (novo), `apps/api/src/modules/tables/service.ts` (`tryCreateSession`/`joinExistingSession` como transações separadas). Padrão a seguir em qualquer fluxo futuro que precise "tentar criar, cair para achar o existente" sob um índice único: nunca dentro da mesma transação.

## ADR-032 — Idempotência real via `INSERT ... ON CONFLICT DO NOTHING` na MESMA transação (não duas transações separadas); `sequence_number` de pedido é um contador simplificado (aceita, M8)
**Contexto:** M8 precisa que a mesma `Idempotency-Key` (double-tap do cliente, timeout+retry) nunca crie dois pedidos, incluindo sob concorrência real (duas requisições simultâneas). `idempotency_keys` existe desde o M1 (nunca usada até agora).
**Decisão — por que aqui a solução é UMA transação, ao contrário do ADR-031 (M6):** no M6, o problema era uma violação de índice único que ABORTA a transação — por isso a solução exigia duas transações separadas (tentar, e se falhar, uma segunda transação para o fallback). Aqui o mecanismo é diferente: `INSERT ... ON CONFLICT DO NOTHING` **não levanta exceção** em caso de conflito — ele silenciosamente não insere nada e devolve zero linhas de `.returning()`. Como não há exceção, a transação **não é abortada**, e dá para continuar consultando/decidindo dentro da MESMA transação. Sob concorrência real, o Postgres serializa isso da forma certa por conta própria: a segunda requisição com a mesma chave BLOQUEIA no `INSERT ... ON CONFLICT` até a primeira transação terminar (commit ou rollback) — só então decide se houve conflito de verdade. Resultado: nunca duas requisições "ganham" a reivindicação da mesma chave ao mesmo tempo, sem precisar de nenhum lock explícito adicional. `apps/api/src/lib/idempotency.ts` (`withIdempotency`) implementa isso de forma reaproveitável para qualquer mutação crítica futura (pagamento, cancelamento, M11+).
**Efeito colateral desejado:** se `fn()` (a criação do pedido) falhar (ex.: item indisponível), a transação inteira — incluindo a linha de `idempotency_keys` recém-reivindicada — é desfeita pelo rollback. Ou seja, uma tentativa que falhou por um motivo de negócio (não um bug) **libera a chave** para uma nova tentativa com o mesmo `Idempotency-Key` depois de corrigido o problema — comportamento correto, provado em teste (`orders.test.ts`, "item indisponível: 422, nenhuma linha criada").
**Decisão 2 — `sequence_number` (número do pedido para o operador ler em voz alta/no ticket) é um contador simplificado (`COUNT(*) + 1` por tenant), não reseta por dia operacional:** o valor correto (`DOMAIN_MODEL.md §1.5`) depende de `tenant_settings.business_day_cutoff` e de um conceito de "dia operacional" ainda não implementado. Sem um índice único garantindo unicidade, dois pedidos concorrentes podem em teoria receber o mesmo número (colisão rara, cosmética — não afeta dinheiro nem isolamento, já que `orders.id` continua sendo a chave real). Registrado como limitação conhecida; corrigir quando o relatório diário real (Fase D) precisar de um número estável e sem reset manual.
**Consequência:** `apps/api/src/lib/idempotency.ts` (novo, reaproveitável), `packages/db/src/schema/orders.ts`, `apps/api/src/modules/orders/service.ts`. Nenhuma mudança em `idempotency_keys` (schema do M1 já estava correto para este uso — `UNIQUE(tenant_id, scope, key)` é exatamente o índice que o `ON CONFLICT` precisa).

## ADR-033 — SSE via polling do outbox (não LISTEN/NOTIFY); token de dispositivo por query string só no `EventSource`; transição de ticket via `UPDATE ... WHERE status = $de` (aceita, M9)
**Contexto:** M9 precisa que o KDS veja pedidos novos "em tempo real" sem reconstruir a infraestrutura de pub/sub do zero.
**Decisão 1 — o "push" do SSE é um polling periódico (700 ms) do outbox `domain_events`, não `LISTEN`/`NOTIFY` do Postgres.** `LISTEN/NOTIFY` exigiria uma conexão dedicada por assinante e código de gerenciamento de conexão adicional; polling do outbox (que já teria que existir para o replay via `Last-Event-ID`, `domain_events.seq` bigserial do M1) é mais simples e já resolve os dois problemas (novo evento + replay) com o mesmo mecanismo. Reavaliar `LISTEN/NOTIFY` só se a latência de ~700 ms deixar de ser aceitável (ex.: múltiplas centenas de dispositivos simultâneos por tenant — não é o caso do Bella III).
**Decisão 2 — o token de dispositivo pode vir por `?deviceToken=` além do header `X-Device-Token`, só quando o header não vem.** `EventSource` do browser não permite headers customizados (limitação da própria API Web, não do projeto) — é a única forma de autenticar essa conexão específica a partir do `apps/web`. Tradeoff aceito conscientemente: o token de dispositivo já é revogável a qualquer momento (ADR-025) e a conexão roda na rede local do restaurante; token em query string pode aparecer em logs de acesso do servidor — mitigação futura se necessário: um token de curtíssima duração só para abrir o stream, trocado à parte do token de longa duração (não implementado agora, registrado como possível melhoria).
**Decisão 3 — bump de ticket usa `UPDATE production_tickets SET status = $novo WHERE id = $id AND status = $antigo` (não `SELECT` seguido de `UPDATE`).** Isso faz o próprio Postgres decidir atomicamente quem "venceu" quando dois KDS bumpam o mesmo ticket quase ao mesmo tempo — o vencedor recebe a linha atualizada, o perdedor recebe zero linhas afetadas e a rota então relê o estado atual e devolve como sucesso idempotente (não erro), exatamente o comportamento pedido por `DOMAIN_MODEL.md §2.6`.
**Consequência:** `apps/api/src/modules/realtime/{service,routes}.ts` (novo), `apps/api/src/modules/kds/{service,routes}.ts` (novo), `apps/api/src/modules/identity/devices/require-device.ts` (aceita token por query também), `pairing_codes.station_ids` (nova coluna, migration `0007`) propagada para `devices.station_ids` na troca do código.

## ADR-034 — Acompanhamento do cliente por polling (não SSE); envio de pedido finalmente ligado ao carrinho; chamados e expedição numa tela só (aceita, M10)
**Contexto:** M10 precisa que o cliente veja o próprio pedido evoluir e chame o garçom/peça a conta. Testando de ponta a ponta pela primeira vez, dois problemas REAIS de produto apareceram (não hipotéticos — pegos ao usar a tela de verdade, não só lendo o código):
1. **O botão "Ver carrinho" nunca chamava `POST /public/:tenantSlug/orders`.** A API de criação de pedido existe desde o M8, mas nenhuma tela do cliente jamais foi ligada a ela — o carrinho só mostrava total e não fazia nada ao clicar. Corrigido: `CartScreen` (novo) lista os itens, deixa ajustar quantidade e um botão "Enviar pedido" chama a API de verdade com a `Idempotency-Key` já gerada pelo carrinho (M7) — a peça que faltava para o ciclo do restaurante fechar de ponta a ponta de verdade, não só tecnicamente por trás.
2. **Status de item (`order_items.status`: `queued`/`preparing`/...) aparecia cru na tela** (ex.: "queued" em vez de "Na fila") — o mapa de tradução só cobria os status de PEDIDO (`orders.status`), não os de ITEM, dois conjuntos de valores parecidos mas diferentes. Corrigido.
**Decisão 1 — acompanhamento do cliente é por polling (a cada 3s), não SSE dedicado para guest.** O M9 já resolveu SSE para dispositivo (KDS); estender para `guest` exigiria uma segunda forma de autenticar o stream (cookie em vez de token) e filtrar eventos por sessão de mesa — complexidade real para uma exigência ("muda em <3s") que polling simples já cumpre. Reavaliar só se o polling se mostrar insuficiente na prática (ex.: custo de requisições com muitas mesas simultâneas).
**Decisão 2 — chamados (`service_requests`) e expedição (tickets prontos) dividem UMA tela de staff (`/admin/service-requests`)**, não duas — registrado no `ACTIVE_PLAN.md` como corte de escopo consciente para não multiplicar telas neste milestone.
**Achado de processo (QA, não bug):** as duas telas novas (`/admin/devices`, `/admin/service-requests`) tinham `if (!tenantId) return null` sem tratar `loading`/`error` do contexto de tenant — ficavam em branco em vez de mostrar carregando/erro, violando `FRONTEND_GUIDELINES.md §7` (4 estados obrigatórios). Só apareceu testando de verdade no browser (a API fake usada para o smoke não tinha `/v1/me/tenants`, simulando exatamente o caso real de erro de rede). Corrigido nas duas.
**Consequência:** `packages/db/src/schema/tables.ts` (`service_requests`, migration `0008`), `apps/api/src/modules/{tables,orders,kds}/{service,routes}.ts`, `apps/web/src/components/customer/customer-menu.tsx` (reescrito: `CartScreen`/`OrdersScreen` novos), `apps/web/src/app/(admin)/admin/service-requests/page.tsx` (novo).
